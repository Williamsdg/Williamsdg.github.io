01

Verified facts about their store

Everything here was checked against the live store, not assumed. Two findings change decisions.

Finding 1 — new customer accounts are already live

/account/login returns a 302 to account.shopcloverandbee.com, which CNAMEs to shops.myshopify.com. That is Shopify's new customer accounts experience, hosted by Shopify on its own subdomain.

This corrects an earlier read of mine. The homepage JSON carries customerAccountsEnabled:"false", which I previously took to mean classic accounts. The redirect proves otherwise. It matters because it flips two decisions in our favour:

— The Customer Account API is available, so order history and profile work is viable rather than blocked.
— Login already lives on a Shopify-controlled subdomain, so moving the apex to the new storefront does not touch it. Accounts, order history and Smile.io points keep working on day one with zero build effort. The contract's promise to preserve customer accounts is satisfied by doing nothing.

Finding 2 — the DNS picture has a third record

account.shopcloverandbee.com → shops.myshopify.com. My earlier subdomain scan didn't probe account and missed it. It stays pointed at Shopify, so the "two records change" statement to Bryson remains true — but the GoDaddy zone export before cutover is now mandatory, not just good practice.

03

Stack decisions

Hydrogen on Oxygen, not Next.js on Vercel

The concept spec said Next.js. The production build should use Hydrogen (Remix-based) deployed to Oxygen. Three reasons, in order of weight:

  • Oxygen hosting is included with their Shopify plan. That removes the hosting line from the $50/month entirely, which matters when the monthly has to cover real infrastructure at a $2,000 project price. Verify plan eligibility before promising it.
  • Customer Account API support is first-class in Hydrogen's tooling, including typed access for logged-in experiences. On Next.js that is hand-rolled.
  • Caching, cart and analytics primitives ship with the framework rather than being assembled.

The cost is Remix rather than Next. For a solo build at this price, included hosting and built-in commerce plumbing beats framework familiarity.

04

Theme architecture

Eight themes are not eight websites. One component system reads a token set and a content record.

Scheduling without a scheduler

Metaobjects have no native "activate on date" behaviour, and that is fine — we do not need one. Store startDate and endDate on each theme and resolve the active theme at request time:

activeTheme(now) =
  themes
    .filter(t => t.enabled)
    .filter(t => t.startDate <= now && (t.endDate == null || now <= t.endDate))
    .sort(by priority desc, then startDate desc)
    [0]  ?? evergreen

"Activate now" simply writes today's date into startDate. "Schedule" writes a future one. No cron, no Shopify Flow, no background job, and no state that can drift out of sync with what Bryson sees in admin.

Caching consequence

If pages are cached and the theme is resolved per request, a midnight switch would serve stale pages. Cache the theme lookup for a short TTL (5 minutes) and include the resolved theme id in the page cache key. A theme change then appears within five minutes without a deploy — and the admin "Publish" button is honest rather than aspirational.

Priority resolves overlaps

Game Day (Aug 15 – Nov 30) overlaps Fall. Rather than forbidding overlap, give each theme a priority integer and let the higher number win. Game Day sits above Fall; Evergreen is priority 0 and has no dates, so it is always the fallback.

Product metafields

Only two are genuinely needed, because their tags already carry season, occasion and team:

  • custom.fit_notes — multi_line_text. Highest-value returns reducer on a dress-led catalogue.
  • custom.model_stats — single_line_text. "Model is 5'8", wearing S".
Why so few

The concept spec proposed eleven metafields. Their tag taxonomy already encodes season, occasion, colour, team, price band and staff picks across 250 products. Adding metafields that duplicate existing tags would create two sources of truth and a data-entry burden for staff. Read the tags.

06

Theme tokens

Every theme writes the same keys. Components never reference a hex value.

{
  "background":        "#F7F4EE",   /* page ground            */
  "surface":           "#FFFDF9",   /* cards, sheets, menus   */
  "surfaceAlt":        "#EEE9E0",   /* banded sections        */
  "text":              "#20201E",
  "muted":             "#76736D",
  "accent":            "#526653",   /* CTAs, active states    */
  "accentSecondary":   "#AAB7A4",
  "border":            "rgba(32,32,30,.12)",
  "heroTreatment":     "full" | "split" | "editorial",
  "displayFont":       "serif" | "serifTight",
  "motionPreset":      "calm" | "editorial" | "signature"
}

Applied as CSS custom properties on <html> at the server render, so there is no flash of the previous theme and no client-side theme JavaScript.

Contrast gate

Every theme must pass 4.5:1 for text on background and on surface, and 3:1 for accent as a boundary. Write this as a unit test over the token sets, not a manual check — eight palettes edited by a non-designer will otherwise drift into unreadable at some point. The Fall and Holiday sets in §07 are the ones to watch.

10

Motion hierarchy

Expensive because it moves well, not because everything moves.

LevelDurationToolApplies to
1 · Micro100–250msMotionButtons, cards, hovers, swatches
2 · UI250–450msMotionMenus, cart, filters, bottom sheets
3 · Editorial600–1000msGSAPHero, masked reveals, campaign transitions
4 · Signature1–2sGSAP / R3FOne or two moments site-wide. Shop My Season is the first

Reduced motion

Under prefers-reduced-motion: reduce: no parallax, no pinned sequences, no WebGL movement, transitions shortened to level 1, simple fades retained, and every section rendered at its final state. Test it rather than assume it — it is the most commonly broken thing in sites built this way.
